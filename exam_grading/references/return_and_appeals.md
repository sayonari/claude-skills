# 返却手順と疑義申告対応

**この章は事故が起きやすい。返却作業に入る前に必ず通読すること。**

---

## 1. 【最重要】共有フォルダのリンクを課題文に載せてはいけない

### 何が起きたか（実例・同一年度に2回発生）

- 各学生の成績PDFは `DriveApp.addViewer(本人メール)` で**ファイル単位**で共有した（これは正しい）
- しかし LMS（Google Classroom）の課題説明文に**成績PDFフォルダのリンク**を載せた
- フォルダ自体は誰にも共有していないため、リンクを押した学生は全員「アクセス権をリクエスト」画面になり、
  **教員宛にアクセス権リクエストが殺到した**

### 原理（誤解しやすい点）

- Google Drive では **ファイルの閲覧権はフォルダに波及しない**。
  フォルダの閲覧権がなければ、フォルダリンクからは「自分に共有された分」も含めて**一切何も見えない**
- **`DriveApp.addViewer()` は共有通知メールを送らない仕様**（Drive画面から手動共有した場合と違う）。
  何もしなければ学生にはリンクが一切届かない
- 学生の正しい導線は次の2つだけ:
  1. **直リンクの一斉メール**（スクリプトで送る）
  2. Drive の **「共有アイテム（Shared with me）」**（共有された時点で自動的に表示される。学籍番号でDrive検索も可）

### 絶対にやってはいけないこと

- ❌ 課題文・授業ページにフォルダリンクを載せる
- ❌ 届いたフォルダへのアクセス権リクエストを承認する
  （**承認するとその学生が全員分の成績PDFを閲覧できる**。全て放置してよい）
- ❌ 教員が手動作成した課題に API で点数を入れようとする（`@ProjectPermissionDenied` になる。
  課題は必ずスクリプトで作成したものを使う）

### 再発の原因と対策

中間テストで事故 → 手順書に教訓を書いた → 期末では**別ファイル**（教訓のない旧テンプレート）を
コピー元にしたため**同じ事故が再発**した。

> **教訓は必ずスクリプト本体とテンプレート文面そのものに埋め込む。**
> 別置きの手順書は読まれないことがあるが、実行するスクリプトは必ず開かれる。

`scripts/appsscript_return_template.gs` は、この教訓をヘッダコメントと件数チェックとして埋め込んである。

## 2. 返却の実行順（この順序を守る）

```
1. createAssignment()  … LMSに課題を「下書き」で作成
                          ※説明文にフォルダリンクを載せない。「共有アイテムから開く」手順を書く
2. PDFをDriveフォルダにアップロード → 【アップロード完了を目視確認】
3. shareFiles()        … 本人のみ閲覧共有
                          ※ログの共有件数＝名簿人数を必ず確認
                          （実績: アップロード完了前に実行し 98/132件で一度失敗した）
4. sendLinks()         … 【必須】各学生に本人PDFの直リンクをメール送信
                          （Google Workspace の送信上限は1500通/日。130通程度は問題ない）
5. postGrades()        … 点数反映・返却
```

**チェック**: 3 の件数が名簿人数と一致するまで 4 に進まない。

## 3. 返却物の設計

| 成果物 | 内容 |
|---|---|
| **個人成績PDF** | 成績票（合計点・大問別得点・小問別の点数と転記・講評・AI返信）＋赤入れ答案（表裏2p） |
| **採点結果Excel** | 成績一覧・統計・度数分布・大問別得点率・flags一覧（教員用） |
| **採点サマリレポートHTML** | 統計、要確認リスト、インジェクション一覧、AI返信一覧（教員用） |
| **学生コメント返信用Excel** | 「教員に一言」の一覧。教員が返信欄に記入 → 成績票にマージして再配布 |

### 返却告知に必ず書くこと

- **「AIは読み間違いをすることがあります。必ず自分の答案と照合して、疑義があれば申告してください」**
  （教員指示・以後の標準。申告歓迎の姿勢が AI採点への信頼につながる）
- 疑義申告フォームのURLと**締切**
- 成績PDFの開き方（**Driveの「共有アイテム」から開く**／直リンクメールを見る）
- これが速報であり、確定成績ではないこと

## 4. 疑義申告の審査

### 審査原則

1. **「答案に書かれた内容で採点する」** — 申告文では正しくても、答案にそう書いていなければ認めない。
   この一貫性が回答文の説得力になる。
2. **別解の認否は満点先例との整合で決める** — 同型の答案を既に満点にしていれば認める。矛盾する判定をしない。
3. **学生の「消して書き直した」申告は基本的に信憑性が高い** — AI が「意図的な筆画」と判定したものが
   学生申告で覆った実例が複数ある。筆画の太さ・濃さの対比＋同一答案内の他の筆跡との比較で判定する。
4. **大規模一括修正になる案件は、教員に「維持か一括かの二択」で政策判断を仰ぐ**
   （個別加点は不公平になる）。実例: 講義実装に沿った別解を満点扱いにする判断で57名が一括+2点。
5. **申告との突合は必須** — 汎用の全数再検証をすり抜けた誤りが、学生申告で判明した例がある。

### 進め方

```
フォーム回答（スプレッドシート）を受領
   → 申告ごとに該当箇所をクロップ＋拡大
   → 判定案を作成（認容/却下・根拠・先例との整合・影響点数）
   → 証拠画像を埋め込んだ判定案HTMLで教員承認（teacher_review.md と同じ形式）
   → パッチスクリプトで反映 → 帳票・PDF再生成
   → 変更一覧の作成／却下分は回答文案も作成
   → 再配布
```

### 再配布の注意

- **同名ファイルを再アップロードすると別ファイル扱いになり、共有が切れる。**
  Apps Script でファイルの**中身だけ更新**する（`updateFiles` 方式）と共有を維持できる。
- 返却済みの提出物に対する `return` 再実行は `Precondition failed` エラーになるが**無害**
  （点数の patch 自体は成功している）。返却済みをスキップする実装にしておくとログが読みやすい。
- 修正を反映したら**変更点を学生に告知**する（LMSのストリーム投稿＋個別コメント）。

## 5. ブラウザ代行作業の制約（AIが代行する場合）

- **Drive Web への自動アップロードは不可**（合成ドロップは `isTrusted` 検査で拒否される）。
  → 教員にフォルダごとドラッグ&ドロップしてもらうのが最速。
- **学生の個人情報（メール・点数一覧）をスクリプトでページに注入する操作は安全機構にブロックされる**ことがある。
  → 有効な分担: **AIがエディタの該当ブロックを選択状態にし、`pbcopy` でクリップボードに新内容を用意 → 教員が Cmd+V を押すだけ**。
- 短い非個人情報テキスト（フォルダID等）はキー入力で通る。ただしエディタの自動括弧補完で
  余分な文字が入るので必ず検証する。
